# 接入一个游戏

启动器通过 `python3 run.py --adapter 名称` 加载项目内的 `adapters/<名称>.py`。模块提供两个同步函数，`root` 是该局的状态目录。最小例子见 [sandbox.py](../adapters/sandbox.py)，带地图与交互物的例子见 [doorworld.py](../adapters/doorworld.py)。

## 把玩家可获得的信息交给模型

`observe(root)` 返回 JSON 可表示的快照。未就绪时，返回 `ready: false` 和等待原因 `reason`，有未决动作时仍应提供最新回执。就绪时，运行时使用以下字段。

| 字段 | 含义 |
| --- | --- |
| `session`、`revision` | 非空字符串。重开游戏更换会话；任何会影响选择、执行前提或目标的变化都要更新版本。 |
| `observed_at`、`valid_for` | 在游戏端实际采样的 Unix 时间及快照有效期，单位为秒。 |
| `goal`、`facts` | 当前目标与玩家可获得的现场信息，例如任务文字、位置、朝向、背包、地图。完整度由适配器负责。 |
| `actions` | 当前可选操作的列表。每项有唯一的非空字符串 `id`，可附说明或可预知的即时效果。目标或物品可以绑定到 ID。可填 `numbered: true`，在模型看到的候选清单里以编号代替长 ID。 |
| `routes` | 可选。按地标给出距离和抵达它的第一个原生动作。 |
| `last_result` | 最近的实际动作回执，需能按动作 ID 与游戏会话对应。 |

有地图时，由适配器决定能读取的地图范围及地标。MiniGrid 示例显式开启全图模式；其他游戏可从玩家能打开的地图或已探索区域构建路线。`runtime/navigation.py` 的 `route_options(start, neighbors, landmarks)` 支持有限图上的等代价有向边及多个抵达位置。可以把朝向纳入节点，或由游戏自己的导航服务给出首步。例如，`{"出口": {"distance": 3, "first_action": "forward"}}`。不可达用 `null`，已抵达用距离 0 和空首步。运行时会把可走的路线首步显示为编号候选，并附剩余步数和当前原生动作。

- MiniGrid 在 `facts.objects` 提供可见的钥匙、门、球和箱子的类型、颜色与位置，以及门的当前状态。
- 这些字段取自当前全图编码。拾取、放下和开门的即时效果按面前格与当前库存计算，实际结果由原生回执确认。
- 手持物品又面对可拾取物品时，地图可提供一条走到空格面前的路线。何时放下以及具体要搬运什么仍由模型决定，已有游戏回执的字段保持兼容。
- 如果有效交互的预测与原生回执不符，或添加新物品类型后读图失败，应对照游戏编码、库存与原生回执。

MiniGrid 可以在角色持有物品、正对可拾取物、身边有空格且剩余步数足够时，提供一次提交的「放下手中物品并拾取面前物品」。

- 候选绑定两件物品和两个格子，执行前按当前版本重算。只有原生背包与两个格子都确认变化后才提交，回执的 `native_actions` 列出每次原生输入。
- MiniGrid 用固定种子重放确认状态。已提交的原生步骤和该意图的回执共用一次日志写入，重启可从最后一步恢复同一回执。
- 一次动作会消耗四步或六步。候选只使用原地转身可达的空格，模型可以自行选择单步操作。
- 如果同类候选频繁让任务倒退，或已有回执的动作在恢复后重复执行，应核对候选选取记录、原生步数和意图 ID。

开着地图路线选项时，MiniGrid 会从公开地图为唯一可见锁门生成「用同色钥匙开门」候选。必要时先把一个球挪到空格，拿起球后可以走一步再放。如果需要暂放手中的钥匙，候选会写明格子，开门前会取回钥匙。

- 模型选择是否开门。提交前按当前会话和版本重算路线，日志提交前核对钥匙、门的状态及有无移动的球。
- 动作依赖公开地图、同色钥匙的可达性和空格。重启使用相同的原生动作记录恢复结果。
- 一次提交最多执行 32 个原生输入，并受关卡剩余步数约束。候选明确给出实际输入数，原生单步操作仍可选择。
- 开门回执与原生地图不一致、常遇到可清除的障碍却没有候选，或候选让观察变慢时，应核对路线、动作步数和原生回放。

## 提交与回执

`act(root, intent)` 接收 `id`、`session`、`revision`、`action`、`expires_at`，也可能附带模型选择的 `subgoal`。适配器在实际执行边界复核前提，按意图 ID 去重，回传相同 `id`、`session`，并提供下列状态和结果证据。

| 状态 | 运行时行为 |
| --- | --- |
| `completed`、`failed`、`cancelled`、`rejected` | 记录终态。完成的动作会触发立即重读。 |
| `accepted`、`running`、`unknown` | 保留待核实的意图。持续在 `last_result` 提供匹配的回执，直到确认终态。 |

运行时把待核实意图写在环境目录，重启后继续检查。执行端丢失回执时，该环境会等待核实。长时动作应由游戏端跟踪，适配器函数快速返回。切换游戏时使用独立的状态目录，同一状态或运行目录只允许一个工作进程。适配器是启动者选择的可信本地代码。

有持久化游戏记录的适配器可实现 `reconcile_pending(root, intent)`。运行时在同一局恢复后、缺少匹配回执时持有环境锁调用它。该函数只核对已经发生的结果，证据不足时返回 `None`，能确认时保存并返回匹配动作 ID 和会话的终态回执，并让 `observe` 继续报告该回执，直到出现更新的动作结果。

模型可调用 `game_observe` 刷新现场，通过 `game_schedule` 提交当轮的一个候选动作。运行时在下发前复核会话、版本、有效期、候选项和路线首步。独立观察进程持续读取快照，动作提交后会唤醒观察进程。模型可见当前会话最近最多八个有结果的动作。短期记录会保留执行失败的原因、已经确认的主动叫停，以及因外部事件中断前已观测到的效果。晚到的确认可以补充同一条记录。适配器可以用 `effect` 记录实际观察到的变化，用 `interruption` 中的 `confirmed` 和 `subgoal` 记录叫停的确认与原因。这段短期摘要保存在当前进程中。

- 承诺观察、查询与说明可以和实际动作同轮进行。只想维持或观察时用 `hold: true`。动作到达执行边界后，后续提交会得到明确的拒绝原因。
- 依据是同一轮的游戏工具按顺序执行，游戏动作仍由适配器校验和确认。
- 接受每轮最多两批只读查证后进入选择。同一情况的明确拒绝或截断可立即修正一次。
- 如果有效动作又在到达游戏前被拦、一次判断连续查询目录，或同轮出现两次游戏下发，应核对工具批次及执行回执。

- 候选清单里的每项都显示 `choice`。`game_schedule` 接受这个编号或候选的字符串 ID，只提交其中一项。目录查询结果仍提供可直接提交的动作 ID。
- 编号依赖适配器的稳定 ID。同一轮刷新时沿用原绑定，执行边界继续核对原 ID 和当前会话。
- 普通候选同时显示 ID 和编号，占用少量额外上下文。`action` 中无歧义的正整数文本可按当轮编号解释，当轮出现过的真实数字 ID 仍按原 ID 校验。编号仅在该轮有效，候选消失后旧编号会被拒绝。
- 若刷新让编号指向其他目标、候选清单显著增长，或有效候选仍频繁被拒绝，应对照候选清单、工具提交和游戏回执。

## 长动作的途中决策

- 承诺。自主游玩用观察或下一步动作附带活动反馈，兼容把误传的整局完成参数当作观察。分阶段活动的启动和实际结算都由原生游戏数据确认。
- 假设。活动的原生 ID 能关联到本会话已启动的动作，原生结算随新游戏帧送达。观众留言身份随施放记录保存。
- 代价。活动结算补写到原有动作记录，启动回执继续释放接单占用。仪表盘在现场结算到达时更新结果，模型可以同一轮回复并继续游玩。
- 重审信号。旧活动被算作新留言的结果、启动就报成功、结算后同一反馈仍反复被拒时，对照留言 ID、动作 ID 和原生终态。

在同一会话有待决意图时，运行时继续维护现场并开放“保持当前意图”。直接返回文字也是一次有效判断。匹配到进行中的游戏回执时，适配器可通过 `cancel(root, parent, request)` 提供可撤销动作，或在 `ongoing.id` 上声明一组途中控制并实现 `review(root, request)`。这些函数须快速返回，按意图 ID 去重，在实际生效时核对控制权。只有游戏能确认物理效果。普通的行动候选在执行器占用时仍与途中控制隔离。

游戏已暂停当前动作的推进且适配器提供了可用的下一步时，可返回 `ongoing.requires_action`。适配器给出实际能推进的候选，运行时省略默认的 `agent:continue`。模型仍可用 `game_observe` 主动观察。

可选的 `situation` 是当前有决策意义的游戏状态，必须包含非空字符串 `key`，其他字段给出可核对的现场事实。只有会改变策略的状态变化才更新 `key`，同一状态内的精细数值可以刷新。运行时把变化前后一起送进同一轮决策，可打断原定复核或回执等待。提交携带 `situation_key` 时，执行前会和最新观察核对。模型用现有的 `subgoal` 或 `assessment` 说明选择依据。

途中候选可声明 `relation: parallel` 或 `relation: replace`，分别表达与当前活动兼容的操作，或由同一执行器交接执行方式。两者沿用 `review` 和原动作 ID，适配器负责在游戏内验证并写入对应回执。通过 `ongoing.activity` 报告游戏已确认的执行方式。普通的途中调整仍可沿用原有候选写法。

`ongoing.trigger` 描述进展或变化，例如道路阻塞。`decision_event` 可补充适配器识别的变化。会话或目标切换、动作终止及进入 `ongoing.requires_action` 阶段可以取消旧推理，其他现场变化进入最新快照。每轮工具固定在最初的游戏会话与父意图上，提交时仍核对当前候选、版本和有效期。执行端不能中止的动画可以自然结束，模型在此期间可以观察、评估和保留下一步意图。

用户要求“跟随一段时间，然后主动结束”时，最后一步的证据可以是主动停止。原动作的回执使用 `status: cancelled`，适配器在同时取得终止指令的游戏确认后填写 `interruption.confirmed: true`。模型可用该回执 ID 登记本次目标完成。目标丢失、外部接管或指令过期都没有这项停止证据。

`last_assessment` 保存当前父意图上最近提交的公开判断与当时的进度，经过确认的物理动作另列在行动历史。模型慢或服务重试时，观察进程持续独立采样。`perception.json` 的序号、游戏采样时间、待决意图和回执状态可用于核实这一点。
### 持续动作期间的决策

- 承诺一直采样。动作在途时，上一轮模型请求结束后用新采样发起下一轮。适配器可以用 `continuous_activity: true` 登记独立于主动作的持续活动，例如开启交战后原地观察。
- 依据是游戏端持续执行已接单的动作，模型基于最新现场和已确认回执决定是否改变策略。维持判断可以提交 `game_observe`，游戏沿现有路线继续。
- 代价是持续行动期间模型调用增加。一次保持一个模型请求，关键变化可中止过期判断。明确的时间目标和物理回执都可以作为判断依据。
- 若相邻轮次之间出现额外定时间隔、复用了旧快照、或观察判断导致同一动作重新启动，应核对采样和工具轨迹。

进行中的动作可以通过 `ongoing.control_families` 提供稳定的复核类别。类别、候选和 `ongoing.trigger` 的变化可以反映在下一轮判断。提交时仍要验证具体动作和实体是否可用。

适配器可为明确的用户指令返回 `direct_user_action`，值是当前父动作的可用途中操作。它需要用户目标 ID，运行时使用同一会话、版本校验和原生操作入口提交。

- 明确的当前用户操作在下一次有效观察后直接提交。同一目标和父动作的提交 ID 可重建。只有提交被明确拒绝且原因为 `observation_changed` 时才立即刷新一次，当前指令、父动作和直接选项仍匹配时可用原 ID 再提交一次。
- 适配器负责判断当前命令是否精确指向一个可用动作，原生回执负责确认结果。
- 接受命令和动作产生效果各有回执。结果未知时以回执和新游戏帧核实。直接操作失效后使用新鲜现场继续正常决策。
- 如果旧命令在新目标下生效、同一操作重复提交，或直接操作失败后卡住，应按目标、父动作和回执 ID 核对。

适配器可用 `direct_user_completion` 提供一句可核验的完成说明。当前用于明确的用户停令，回执必须属于本会话、本条指令，并确认原动作已被取消且实际停稳。

- 运行时以同一原动作回执登记完成，随后保持观察。新指令使用新一轮现场。
- 适配器提供物理结果的证据，运行时同时核对回执归属、执行器是否空闲和各项完成条件。
- 接受操作和物理确认之间继续采样。证据过时或缺少完成条件时，继续按现场判断。
- 若旧回执被用来完成新任务、完成后仍重复提交，或实际尚未停稳却登记完成，应核对新鲜游戏帧、最新指令 ID 和回执 ID。


- 动作回执为 `accepted` 且唯一候选是继续观察时，模型仍接收新鲜的判断轮次。`ongoing.game_control_state` 描述即将启动动作、途中操作尚待确认或游戏仍在完成效果。
- 游戏回执和实际能力决定候选是否可提交。相同请求继续受原动作有效期约束。
- 在游戏效果进行期间继续判断可以及时处理新指令和现场变化。代价是在只能观察的短暂阶段也可能发起模型请求。
- 如果旧操作被重新下发、观测仍引用旧回执或新指令没有及时生效，核对动作与目标 ID、原生回执及采样序号。

- 游戏已采纳途中指令、仍在产生实际效果且暂时没有可用的途中操作时，可由 `ongoing.control_effect_pending` 表达。
- 当前游戏状态、途中回执和目标必须属于同一动作。尚未被采纳的控制沿用提交有效期。已确认采纳的控制依照游戏最新观察，适配器在效果停滞、失败或已完成时清除标记。
- 效果进行期间由游戏驱动动作，模型在同一动作下继续判断。
- 如果效果停滞或游戏已完成时仍沿用旧回执，对照当前控制回执、采样序号和模型快照。

- 任务登记定时复核后，运行时在下一次判断里提供 `review_elapsed_s`、`review_remaining_s` 和 `review_due`。若只需等足指定时长且现场符合要求，模型可以执行下一步。
- 经过和剩余时间以同一目标已保存的复核记录计算。适配器提供的 `goal_elapsed_s` 以当前指令开始和游戏采样时间为准。
- 持续行动中时间标记只提供经过时间和目标是否到期。静止且没有持续活动的现场可以用明确期限安排复核。
- 若复核到了仍重复登记同一段等待，或改口后继续按旧时间执行，应核对模型输入、指令 ID 和游戏回执。

### 可恢复的能力阻碍

适配器可以在观察中返回 `blocked_capabilities` 列表。每项提供稳定的 `id`、当前 `reason` 和解除条件 `resumes_when`。可选的 `wake_on` 保存对策略有影响的现场值。模型在没有进行中动作时可用 `game_observe(assessment, wait_for)` 登记其中一项。观察线程持续采样，能力恢复、相关事实或目标改变即重新判断。明确的时间条件可与等待条件一起登记，较早满足的一项唤醒模型。

承诺是让模型明确其等待依据，并让新情况打断等待。依据是适配器能区分能力不可用与可用。未进入唤醒条件的事实仍能被持续观测，模型会在下一次有效事件时读取。出现持续等待或遗漏相关变化时应重审适配器的唤醒条件。
